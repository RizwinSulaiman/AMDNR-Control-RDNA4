# TheAutomatic 1.9.8.1 compatibility note

TheAutomatic `v1.9.8.1` is pinned at commit `9afa534001637ba4852062514c3c7c4124735c1e`; its release asset `OptiScaler-AMD-PreSR-1.9.8.1.zip` is published with SHA-256 `199d156415c40f9110d220a93daae1e55267a5d24c5162da72a90509a3a2a11d`. Its vendored lmxxf source pin is `c809efb0ea2960f148624730898da61b8fb55a45` (0.37-era), with local lifecycle/recovery patches and the System32 `d3dcompiler` / `cs_5_0` fallback in the 1.9.8.1 tag.

Do **not** treat its `LmxxfNrRuntime.dll` as a verified binary drop-in for AMDNR 0.3.4.2 yet. TheAutomatic exposes C ABI v1, but AMDNR's public source snapshot in this fork omits the actual `dlssnr/lmxxf/` host tree and `runtime/LmxxfNrApi.h` that its own README says the host compiled against. That prevents a byte/offset/function-table comparison of the two ABI definitions. TheAutomatic also ships a loose runtime closure (`LmxxfNrRuntime.dll` + `lmxxf-modules/` + `shaders/` + tiled weights), while AMDNR 0.3.4.2 ships its runtime as `LmxxfNrRuntime.dll` + authenticated `LmxxfNrRuntime.pak`. AMDNR's ini explicitly recognizes the older TheAutomatic loose layout, but that proves asset-layout awareness in AMDNR's runtime, not that a newer foreign runtime DLL accepts AMDNR's host struct sizes and lifecycle calls.

TheAutomatic's ABI documentation says ABI version 1 has evolved by `struct_size`, includes a zero-output recovery create flag, `CancelUnsubmitted`, queue-drain/lifetime rules, and newer `LmxxfNrFrameInfo` exposure/paper-white tails. Without AMDNR's shipped host header or a controlled host/runtime ABI probe, replacing the DLL could fail at `LmxxfNrGetApi`, `Create`, or `PrepareFrame`, or subtly violate queue lifetime assumptions. The 0.37 line also inherits lmxxf 0.36's deliberate float-FMA numeric-baseline change, so it is not bit-exact to AMDNR's documented 0.31 kernel lineage.

For these reasons this branch stages **metadata and source pins only**. No DLL/pak replacement package is produced. A safe integration gate is: recover AMDNR 0.3.4.2's exact `LmxxfNrApi.h` (or its released runtime test fixture), compare ABI v1 field offsets/function-table order, then run a no-game `GetApi`/`QueryCapabilities`/create-reject smoke against the candidate runtime. Only after that should the loose module/shader closure be staged.
